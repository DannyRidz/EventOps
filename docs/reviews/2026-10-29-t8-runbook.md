# T8 local operations and production prerequisites

## Maintenance

The separate `npm run worker:retention` process needs private `WORKER_DATABASE_URL` selecting `eventops_worker`, `EVENTOPS_RETENTION_STORAGE_TOKEN` with the same restricted role, Supabase URL/publishable key and an absolute `EVENTOPS_DELETION_LEDGER` path on an independent durable volume. Never place that ledger inside the database backup or source tree. `EVENTOPS_RETENTION_ONCE=1` runs one sweep. No provider key or enabled AI gate is needed.

A sweep durably appends minimal event/account/CSV/audio identifiers before removing due Storage objects or rows. Failed ledger writes stop the sweep. Failed object deletes retry. Purge waits for absent Storage metadata. Opaque ledger records have an eight day expiry, longer than the seven day backup target; operators must rotate expired records only after verifying the oldest recoverable backup. The current writer does not automate ledger rotation. Worker output includes only allowlisted codes and numeric counts. No logger accepts event content or tokens. Logs need host retention of 14 days, aggregate metrics 90 days.

Use `eventops_worker_api.retention_health()` from the restricted operator process to inspect numeric due object count, pending event purges and oldest analysis queue age. Alert delivery, durable worker heartbeats, cleanup lag timestamps and backup age alerts still need hosted integration. Public `/api/health` is liveness; `/api/ready` makes a database function call and exposes only ok/unavailable. Readiness does not certify provider, mail, backup or legal readiness.

## Local drill

Run `node scripts/verify-t8.mjs` against the loopback application after applying migrations. It uses captured local mail and synthetic accounts, files and revisions. It saves a private test ZIP in temporary storage for the recovery drill. Run `T8_PG_DUMP=/absolute/path/to/matching/pg_dump node scripts/verify-t8-recovery.mjs`. PostgreSQL tools must match the server major version. The drill creates two uniquely named temporary databases and removes them in finally. It encrypts a logical dump and object manifest using AES 256 GCM with an ephemeral key, verifies hashes and restores into the isolated target, then applies post backup file/event deletion records. It never replaces the running project. It does not operate a hosted backup schedule or prove provider Storage byte restoration.

## Production recovery procedure, not yet executed

1. Freeze writes, disable all provider gates and stop normal web/worker access to the target. Use an isolated approved target. Never point users at an unverified restored database.
2. Restore the encrypted database artifact and separately copied private object bytes. Check the consistent manifest and every SHA256. A database backup alone has no object bytes. The key and destination credentials belong in a separate secret store.
3. Obtain the independent deletion ledger and reconcile it with the latest deletion requests and cancellations from the authoritative source or its durable outbox. Apply all event/account purges and raw CSV/audio deletions, including database byte receipts, before restoring any access. Missing or incomplete deletion history blocks release of the restored target. In particular, a just requested CSV/audio deletion can precede the next maintenance sweep; a completed sweep alone does not prove that this request window has been reconciled. If latest deletion history cannot be recovered, suppress all restored raw originals and keep affected event/account access disabled pending authorized reconciliation. Do not claim that the database copy of tombstones is independent.
4. Cancel incomplete jobs and invalidate leases; never rerun approvals or external calls. Reconcile model reservations conservatively. Check every current head, parent chain, ownership policy, private storage path and raw receipt. Run cross owner denial, approval rollback, export and deterministic briefing smoke cases.
5. Rehearse application image rollback against the compatible schema. No destructive down migration. Enable access only after verification and record the precise data loss, recovery duration and remaining limits. Communicate only through a separately authorized operator.

The local drill demonstrates mechanics and deletion replay. The production targets remain RPO 24 hours and RTO four hours, unproven. Seven day encrypted independent backups, scheduling, key custody, lifecycle expiry, immutable independent deletion storage, restore into the actual host and object service, backup/retention failure alerts, support ownership and deployment rollback remain launch gates. No resource or payment has been provisioned.

## Other production gates

Complete operator identity, support address, jurisdiction and lawful processing notices with appropriate review. Verify SMTP, session revocation behavior on hosted Auth, country lookup using a licensed current local database and trusted host proxy IP, Meta territories/policies/terms, deployment region and provider locations. Live AI remains disabled, so no geographic processing gate is claimed. Existing shared budgets, active event quotas and collection limits remain enforced locally. Multi process export throttling, a streaming export beyond the current 64 MiB bound and production storage quota/load measurements remain open.
